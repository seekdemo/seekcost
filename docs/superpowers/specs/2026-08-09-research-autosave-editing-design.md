# 研究文章自动保存编辑状态修复设计

## 背景

研究详情页通过 `initialNoteId` 或 URL 查询参数打开指定文章。当前选中文章的初始化副作用同时依赖完整的 `notes` 列表。编辑器触发自动保存时，`notes` 会更新并导致该副作用再次运行，进而清空 `editingId`，让编辑器在第一次修改保存后退出。

## 目标

- 自动保存成功或触发保存时，继续保持当前文章的编辑状态。
- 只有用户点击“完成编辑”、返回研究库、删除文章或主动切换到其他文章时，才退出当前编辑状态。
- 保留现有的 450ms 防抖自动保存与失败提示行为。
- 不改变 URL 兼容、评论加载和文章内容本身。

## 方案与取舍

1. **推荐：让初始选中副作用只响应路由/加载完成**
   - 使用已加载文章列表判断目标是否存在，但不在列表内容更新时重置编辑状态。
   - 优点：改动小、保持现有状态模型，自动保存和手动编辑边界清晰。
   - 风险：需要明确区分“首次打开”和“文章列表刷新”。

2. 为编辑状态增加独立的编辑会话 ID。
   - 优点：可以精细处理并发刷新。
   - 代价：引入额外状态和生命周期，当前问题不需要这么复杂。

3. 自动保存时暂存并恢复 `editingId`。
   - 优点：改动集中在保存函数。
   - 缺点：仍让路由初始化副作用干扰编辑状态，容易在其他刷新路径复现。

本次采用方案 1。

## 交互与数据流

打开 `/research/[id]` 时，待文章加载完成后设置 `activeId`，并仅在目标文章或路由上下文真正改变时清理编辑状态。用户编辑字段后：

1. `updateNote` 立即更新本地文章内容并更新时间。
2. 450ms 防抖后调用 `api.updateNote`。
3. `editingId` 保持不变，编辑器继续可用。
4. 保存失败仅显示已有错误提示，不丢弃本地草稿，也不强制退出编辑。

## 验证

- 静态检查确保详情初始化 effect 不会因 `notes` 内容变化清理 `editingId`。
- 前端 TypeScript、ESLint 和生产构建通过。
- 增加或更新测试，覆盖“进入编辑 → 修改字段 → 自动保存 → 仍可继续编辑”的行为。
